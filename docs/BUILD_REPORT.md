## 4. The `MAX_PATH` failure and its fix

### 4.1 Symptom

The first release build failed inside the New Architecture's native C++
compilation:

```
ninja: error: Stat(rngesturehandler_codegen_autolinked_build/CMakeFiles/
react_codegen_rngesturehandler_codegen.dir/D_/Bright_Cakes_Mobile_App/node_modules/
react-native-gesture-handler/shared/shadowNodes/react/renderer/components/
rngesturehandler_codegen/RNGestureHandlerDetectorShadowNode.cpp.o):
Filename longer than 260 characters
```

and, for the library modules:

```
ninja: error: mkdir(CMakeFiles/reanimated.dir/D_/Bright_Cakes_Mobile_App/
node_modules/react-native-reanimated/Common/cpp/reanimated/CSS/interpolation/
transforms/operations): No such file or directory
```

### 4.2 Diagnosis

`Filename longer than 260 characters` is the Win32 `ERROR_FILENAME_EXCED_RANGE`
error. The New Architecture compiles C++ for every autolinked native library,
and the generated object files are nested deeply under `android/app/.cxx`.

Measured path lengths:

| Segment | Length |
| --- | --- |
| Source path (`D:\Bright Cakes Mobile App\node_modules\…\RNGestureHandlerDetectorShadowNode.cpp.o`) | 179 |
| AGP staging prefix (`android\app\.cxx\RelWithDebInfo\<hash>\<abi>\rngesturehandler_codegen_autolinked_build\CMakeFiles\react_codegen_rngesturehandler_codegen.dir\`) | 174 |
| **Total** | **353** |

The limit is 260. `LongPathsEnabled=1` is already set in the Windows registry
on this machine, but the bundled Ninja is not long-path aware, so the limit
still applies.

### 4.3 Fixes that were tried and rejected

| Attempt | Outcome |
| --- | --- |
| `subprojects { afterEvaluate { … } }` in `android/build.gradle` | *"Cannot run Project.afterEvaluate(Closure) when the project is already evaluated."* |
| `afterEvaluate` + `plugins.withId` | *"It is too late to set buildStagingDirectory. It has already been read to configure this project."* — AGP registers its own `afterEvaluate` first, so the property has to be assigned **during** the module's evaluation |
| `gradle.beforeProject` + `plugins.withId` | Worked for the **library** modules (Reanimated, Worklets) but **not** for `:app` — `expo-root-project` evaluates `:app` before the listener is registered, and the app module's source path (179) plus Ninja's fixed `CMakeFiles/<target>.dir/` segment (93) already exceeds 260 no matter where the staging directory is placed |

The staging-directory override was therefore **removed**, and `android/build.gradle`
is left byte-for-byte as `expo prebuild` generated it.

### 4.4 The fix that worked

This is the remedy Expo documents for this exact error
(<https://docs.expo.dev/troubleshooting/windows-long-paths/>):

1. **Enable long paths in Windows** — already set on this machine:
   `HKLM\SYSTEM\CurrentControlSet\Control\FileSystem\LongPathsEnabled = 1`.
2. **Install a CMake that bundles Ninja ≥ 1.12.0** — Ninja gained long-path
   support in 1.12.0. The Android SDK's default CMake 3.22.1 bundles the old
   Ninja 1.10.2, so `cmake;3.31.6` (Ninja 1.12.1) was installed.
3. **Point Gradle at it** with `android.cmakeVersion=3.31.6` in
   `%USERPROFILE%\.gradle\gradle.properties`.
4. **Delete the stale CMake trees** so they are regenerated with the new
   Ninja: `android\app\.cxx` and `android\app\build`.

> ⚠️ **The BOM trap.** PowerShell 5.1's `Set-Content -Encoding UTF8` prepends
> a UTF-8 BOM. Gradle then silently fails to parse the *first* property in
> the file and falls back to the default CMake 3.22.1 — reproducing the
> original failure with no obvious cause. The file must be written with
> `System.Text.UTF8Encoding($false)`. The build log confirms the override
> took effect: `[ExpoRootProject] Overriding CMake version: 3.31.6`.

## 9. Release signing

The release build type uses the **debug** keystore, because no production
keystore was supplied:

```groovy
release {
    // Caution! In production, you need to generate your own keystore file.
    // see https://reactnative.dev/docs/signed-apk-android.
    signingConfig signingConfigs.debug
    ...
}
```

The APK is therefore **installable and fully functional**, but it is **not**
signed with a Play Store key. To produce a store-ready artefact:

```bash
keytool -genkey -v -keystore brightcakes-release.keystore \
  -alias brightcakes -keyalg RSA -keysize 2048 -validity 10000

# android/gradle.properties
BRIGHTCAKES_UPLOAD_STORE_FILE=brightcakes-release.keystore
BRIGHTCAKES_UPLOAD_KEY_ALIAS=brightcakes
BRIGHTCAKES_UPLOAD_STORE_PASSWORD=…
BRIGHTCAKES_UPLOAD_KEY_PASSWORD=…

# android/app/build.gradle → release signingConfig
signingConfig signingConfigs.release
```

Keystores and their passwords are excluded by `.gitignore`
(`*.jks`, `*.keystore`, `*.p12`).
